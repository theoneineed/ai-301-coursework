## The question

This tool answers exactly one question: **is this ready to submit?**

You evaluate a PR package—a candidate pull request consisting of a title, description, commits, diff, and test evidence. You must read these artifacts strictly against the approved plan it claims to implement and the original issue that plan belongs to.


## Inputs and modes

Execute in one of two modes depending on the context:

*   **Live mode:** Gather and read the user's `plan.md` (including any deviation notes), the branch's diff (which must be generated by running `git diff main...HEAD` from the working copy), the draft PR title and description, and the test evidence. Evaluate these against the target issue. If grading a house-chain student, read the provided house plan and house repro pack instead.

*   **Eval mode:** The provided package bundle is the entire universe. Do not fetch external data, run git commands, or invent context. Execute every check using the full verdict rule.



## The scope seam (live mode only)

In live mode, read `scope.md` before executing any checks. If the `Repo:` line contains an unfilled placeholder, stop immediately and refuse to grade. Otherwise, enforce the rules found within that scope and refuse to grade work outside of the specified repository. In eval mode, ignore `scope.md` entirely.

## The voice seam (live mode only)

In live mode, read `voice-guide.md` and gate the outgoing PR title and description against its rules. Report any broken communication rules in your summary. The voice guide never changes the verdict on its own unless a specific rubric check instructs you to do so. In eval mode, ignore `voice-guide.md` entirely.

## Component reads

You are the executor of three judgment files:
*   Read `rubric.md` to define the checks and the final verdict rule.
*   Read `references/evidence-guide.md` to map exactly where each piece of evidence lives.
*   Read `procedure.md` for the exact operating steps.

Execute the procedure exactly as written. If the procedure is silent on a step, report the gap rather than improvising around it.

**Refusal rule:** If either `rubric.md` or `procedure.md` has no custom content or contains only default template instructions, stop immediately and refuse to run.

## Verdict and output

The verdict space is strictly binary: `accept` (ready to submit) or `reject` (hold).

End your reply with the fenced JSON block below. It must be valid, it must be the final text in your response, and absolutely nothing may follow it.

```json
{
  "item": "<PR URL or bundle id>",
  "checks": [
    {"name": "<check name>", "grade": "pass|fail|unclear",
     "evidence": "<one line: the fact or quote that decided it>"}
  ],
  "verdict": "accept|reject"
}
```

## Grading discipline

You must grade under the following standing rules:

* Evidence first: Do not grade any check without naming the specific fact or quote that decided it.
* Grade the thing, not the polish: Evaluate the artifact itself against the plan, the issue, and the stated standards. Ignore aesthetic formatting.
* The rubric decides: If a check passes its stated condition, it passes. Do not alter a grade based on gut feeling.
* The procedure decides how: Follow the exact steps as written.
* Unclear defaults to fail: Apply the rubric's verdict rule for unclear grades. Where the rule is silent, treat any unverifiable claim as a failing one.
